# Intent: one key press is one key, however slow the desktop

## Problem

A `key` action is sent as two helper lines, press then release. Before each
line, `run_batch` re-reads the control state and checks the target with
`hyprctl` (`control.py:880-893`), and the helper round trips after each
(`ai_mirror_input.c`, `K`). In a `nixarchy-desktop` microvm that puts about
400 ms between the press and the release (foot's `WAYLAND_DEBUG` trace:
pressed at 128517 ms, released at 128914 ms). Clients start repeating a held
key after 250 ms, so one `key RETURN` gave foot three or four Returns.

In a shell that is a few empty prompts. In a panel where Return toggles a row
(`gotchas.md`, the package panel), one Return can act several times. A newline
or tab inside `type` text goes the same way.

## Proposed outcome

A `key` action, and a newline or tab inside `type`, reaches the client as
exactly one press and one release, back to back, on any desktop speed.
Measured in the microvm: one `key RETURN` into foot gives one Return in its
`WAYLAND_DEBUG` trace, with the release in the same batch as the press.

## Affected users and systems

- `src/ai_mirror_input/ai_mirror_input.c`, `src/ai_mirror/input.py`,
  `src/ai_mirror/control.py`, `tests/`.
- Every agent pressing keys through ai-mirror. It is worst in microvms. The
  real desktop is fast enough that it has not been seen there.

## Constraints

- The invariants hold. Ownership and the target are still checked before
  every helper line. `C` releases everything held. Every failure path sends
  `C`.
- `key_down` / `key_up` keep their meaning: an agent that asks to hold a key
  holds it.
- No new dependency.
