# Intent: the accessibility tools hand over a password manager as machine-readable text

## Problem

#19 stopped `screenshot` capturing a rectangle containing a password manager, a
credential prompt, a private browsing window or a banking page.
`a11y_tree` and `a11y_find` have no such guard, and the exposure there is worse.

A picture has to be read. An accessibility tree is already structured: `_node()`
returns a role, a name, bounds, the available actions, and up to 120 characters
of `text` per node. A credential prompt exposed through AT-SPI is not a
photograph of a passphrase field — it is a labelled, addressable, machine-
readable description of one, and `a11y_act` can then act on it.

`src/ai_mirror/privacy.py` already exists from #19 with the patterns and
`kind(cls, title)`. What is missing is where a tree walk applies it.

**What scoping established, and it corrects the guess in the issue:**

1. **The AT-SPI shapes map onto the matcher cleanly.** An application node's
   `name` plays the part of a window class and a frame node's `name` plays the
   part of a title. Measured here: `name='Google Chrome'` at depth 0,
   `name='Inbox (1) - olaf@freundcloud.com - …'` at depth 1. Feeding those to
   `privacy.kind()` returns the right answer for a password manager, a banking
   title, a credential prompt and ordinary windows alike. The mapping I called
   "not obvious" when filing this is in fact direct.
2. **The unit is the frame, not the application.** The issue guessed that
   "refusing per application root is probably right". It is not. One
   `Google Chrome` application node carries a frame per window — six of them on
   this desktop — so refusing the application because one of its windows is a
   bank would remove every Chrome window from the tree. That is the difference
   between a guard and an outage.
3. **Frame names are themselves sensitive, and are already returned.**
   `a11y_tree` reports frame names today, and they carry an inbox count and an
   email address. So this is not only about pruning content; it raises what a
   refused frame should look like in the output at all.

## Proposed outcome

- An accessibility walk does not descend into a window whose contents should not
  be read, and `a11y_find` cannot match inside one.
- The rest of the tree still works. A sensitive window in one application does
  not cost the caller every other window of that application.
- The caller can tell that something was withheld, rather than silently seeing a
  smaller tree and concluding the element is absent — the same failure #18 fixed
  for empty finds.
- Whatever is withheld is withheld without naming it.

## Affected users and systems

- Every agent using `a11y_tree`, `a11y_find` and, transitively, `a11y_act`,
  which resolves an id the tree handed out.
- `src/ai_mirror/a11y.py`: `_walk`, and whatever `tree` and `find` report.
- `src/ai_mirror/privacy.py`, if the matcher needs a second entry point.
- `index.nav()`, which walks with `enable=False` and would inherit any change to
  `_walk`.
- `gotchas.md`, which already documents #19's refusal and would be inconsistent
  if this behaved differently.

## Constraints

- **Must not name what it refused.** #19's refusal names a category and never a
  title, and the same titles are in play here.
- **Must not silently shrink the tree.** A caller that cannot tell withheld from
  absent will conclude the element does not exist, which is the failure #18
  exists to prevent.
- **Must not cost an AT-SPI round trip per node.** The walk is already thousands
  of synchronous calls for a few hundred nodes; a guard that asks each node
  another question makes an expensive thing worse.
- **Must keep `index.nav()` working.** It walks at depth 1 with `enable=False`
  for orientation and must not start refusing or paying for it.
- Tests must not reach the real desktop (#15).

## Open questions

1. **Prune the frame's children, or drop the frame node entirely?** Dropping it
   hides that a window exists at all; keeping it exposes its name, which is the
   sensitive part. Keeping it *without* the name is a third option and is
   probably the right one, but it is a decision.
2. **Does `a11y_find` say anything when it withheld something?** #18 made an
   empty find explain itself. A find that was empty *because* something was
   withheld is a different sentence, and arguably a more important one.
3. **What about a sensitive application, rather than a window?** 1Password's
   application node is itself the signal, and pruning at that level is right for
   it and wrong for Chrome. Both probably need to exist.
4. **Does `a11y_act` need its own check?** It re-resolves an id from the desktop.
   If a tree never handed out an id inside a refused frame, `act` cannot reach
   one — unless the id was obtained before the window became sensitive.
5. **Is `index.nav()` in or out?** It reports which applications expose a tree,
   at depth 1. That is arguably harmless and arguably a leak of what is running.
