# Intent: Let an agent confirm what happened, instead of guessing

## Problem

`input` reports that a keystroke was delivered. It cannot report that anything
resulted from it, because nothing in ai-mirror watches for a result. A caller
is left with two options and both are bad.

It can sleep a guessed interval and continue. That is what corrupts state: the
guess is right most of the time, and the times it is wrong are silent. Timed on
p620, pressing the key that opens the package panel:

```
ai-mirror input returned          164 ms
openlayer>>nixarchy-pkg-menu      225 ms
```

For 61 ms the caller has been told its action succeeded and the panel is not
up. Anything sent in that window lands on whatever is behind it.

Or it can take a screenshot and look. That works, and it costs a round trip
and a model's attention to answer what is usually a yes or no. It is expensive
enough that callers skip it, which returns them to guessing.

This is not a theoretical failure mode. It is precisely what happened during
the session behind #3: a click missed the filter box, four further steps were
sent on the assumption it had landed, the tab count drifted, and a `Return`
intended for an option list queued a **removal of `azure-cli`** into the user's
NixOS configuration. Nothing surfaced it. It was found minutes later by
extracting frames from a finished video, and undone by hand.

The compositor knew. Hyprland's second socket publishes exactly the fact that
was missing, and nothing in this project reads it:

```
openlayer>>nixarchy-pkg-menu
closelayer>>nixarchy-pkg-menu
activewindow>>vesktop,(65) Discord | #discord-suggestions | Omacom
openwindow>>…
workspace>>8
focusedmon>>DP-1,1
activelayout>>hl-virtual-keyboard-ai-mirror-input,English (UK)
```

I should have found this earlier. In #3 I wrote that "the shell answers
`Function not found` to every panel-state query, so this can only be answered
by a screenshot", and filed olafkfreund/nixarchy#749 asking nixarchy to grow an
observation API. Both were wrong about the important half: the compositor has
been broadcasting panel open and close, by name, the whole time. The lesson is
narrower than the bug — I checked one IPC surface, found it lacking, and did
not check the other one next to it.

## Proposed outcome

A caller can act and then state what it expects, and be told whether that
happened:

- press the key that opens a panel, and continue only once that panel is
  actually up, or learn within a bounded time that it is not
- launch an application and continue when its window exists, rather than after
  a sleep long enough to usually work
- switch workspace or monitor and know the switch landed before clicking at
  coordinates that assume it
- notice that the keyboard layout is not what the caller assumed before typing
  into something

Observable difference: the `azure-cli` class of failure becomes impossible to
reach silently. A step that did not take effect stops the sequence instead of
letting four more steps run against a screen that is not the one the caller
believes it is looking at. And the cheap check stops requiring a screenshot,
so callers stop skipping it.

## What this does not fix

`openlayer` proves a panel is up. It does not say which tab has focus, what a
text field contains, or which row the cursor is on — and in the `azure-cli`
failure the drifting tab count is what aimed the `Return`. Confirming the panel
opened would have stopped that sequence, but only because the first step failed;
a later drift inside an open panel is still invisible here.

That narrower problem belongs to olafkfreund/nixarchy#749, where letting
`summon` take `{"query": …, "tab": …}` removes the multi-step sequence rather
than reporting on it. The two compose: confirm the panel is up, open it into a
known state, and there is nothing left to drift.

This also does not make anything faster in wall-clock terms. Waiting for an
event costs the time the event takes. It replaces a guessed sleep that is
either too short to be safe or too long to be pleasant.

## Affected users and systems

- **Any agent driving this desktop**, on any nixarchy host. The benefit is
  largest for scripted sequences, which are exactly the ones that run fast
  enough to outrun the compositor.
- **ai-mirror gains a second, long-lived connection** to the compositor
  alongside `hyprctl`. Verified safe to share: two clients connected at once
  received an identical stream, so a new listener does not starve waybar,
  QuickShell or anything else already subscribed.
- **The ownership gate.** Waiting is observation, but it is observation
  attached to actions that mutate. Whether a wait inherits the gate of the
  action it accompanies is an open question below.
- **The user**, who currently pays for every silent mis-step — in this case
  with an unrequested edit to their system configuration.

## Constraints

- **Must not break existing callers.** Everything that works today must keep
  working unchanged, with waiting opt-in.
- **Must be bounded.** Every wait has a timeout and a definite answer. An agent
  blocked forever on an event that will never arrive is worse than one that
  guessed, because it cannot even be told it was wrong.
- **Must not swallow the answer.** A timeout is a result the caller has to see,
  not an exception that reads like a transport failure. "The panel did not
  open" and "ai-mirror is broken" must not look the same.
- **Must not miss events that arrive too early.** The measured gap is 61 ms;
  anything that connects *after* acting will lose the race it exists to win.
- **Must not leak the connection.** A socket per call, or one shared and
  closed, but never an accumulation. This host already carries 15 `ai_mirror
  mcp` processes that outlived their sessions; it does not need leaked sockets
  too.
- **Must degrade.** A missing socket, a compositor restart or a signature
  change makes waiting unavailable, not fatal. Callers fall back to what they
  do today.
- **No new runtime dependencies**, stdlib Python, per house style.

## Open questions

1. **What shape should this take?** A separate `wait` operation the caller
   invokes after acting is simple and composable, but leaves the 61 ms race
   unless the listener is attached first. An optional `expect` on `input`
   itself closes the race by construction but couples two concerns and grows a
   tool whose schema is already the largest here. This is the central design
   decision and I do not think it should be settled in the intent.

2. **Does waiting require the control grant?** Reading events is observation,
   like `index`. But a wait is normally attached to an action that needed the
   gate, and an agent without control has nothing to wait for. Inheriting the
   gate is defensible; so is not.

3. **How much of the event stream is exposed?** The narrow version matches
   named events a caller nominates. The broad version hands back a window of
   raw events and lets the caller decide, which is more useful for diagnosis
   and much easier to misuse. The stream also names every window title on the
   machine, which is the privacy consideration #3 already ran into.

4. **Should a failed expectation stop a batch?** `input` takes a list of
   actions. If a wait between them fails, continuing is what today's behaviour
   already does badly. Stopping is safer and changes the meaning of a batch.

5. **Is Hyprland's event vocabulary stable enough to build on?** These names
   are a compositor-version contract that nothing in this project pins. 0.56 is
   what is running; a rename upstream would silently turn every wait into a
   timeout, which is the failure mode hardest to notice.
