# Intent: the audit log is the whole safety story, and the CLI cannot read it

## Problem

`control.audit()` writes one JSON object per line into
`$XDG_RUNTIME_DIR/ai-mirror/audit.jsonl` — every request, every answer, every
stop. It is the only durable record that an agent asked for this desktop and
what happened next.

Nothing can read it. The CLI has `status`, `doctor`, `windows`, `mcp`,
`control`, `screenshot`, `input`, `window`, `launch`, `clipboard`, the
`a11y_*` family, `wait` and `index`. To see what an agent did you `cat` a path
under `$XDG_RUNTIME_DIR` — a directory most people could not name — and read
JSON lines by eye.

That is tolerable while the log is a backstop. It stops being tolerable in the
case that prompted this, which is remote use.

**Where this came from.** Downstream, in olafkfreund/nixarchy#1018, the
question was how an agent on one machine should drive another. The answer is
MCP over SSH, because this is a stdio server:

    command = "ssh"; args = [ "desk" "ai-mirror" "mcp" ];

and the consequence — #43 — is that the consent dialog on the far machine is a
notice rather than a gate, because `ssh desk ai-mirror mcp` is a shell on that
account and `ai-mirror control confirm` is an ordinary command. AGENTS.md
states the same invariant: *"The gate is unforgeable only for an agent that
reaches ai-mirror through MCP alone — one with a shell on the same account can
run the CLI. Do not add machinery claiming more."*

Once that is accepted, **the log is not a backstop; it is the safety story.**
You cannot prevent it, you can see it. And the person who needs to see it is
sitting at a different machine, so the natural reach is

    ssh desk ai-mirror audit

which needs nothing anywhere else the moment the verb exists. Nixarchy was
about to wrap this over SSH and stopped: that would be re-exporting this
project's feature from a repository that has nothing to do with it.

**And an empty answer is ambiguous today.** `root()` creates its directory on
every call, so the directory always exists; the file exists only once
something has been audited. `$XDG_RUNTIME_DIR` does not survive a reboot. So
"no entries" and "this machine rebooted and I have not checked since" look
identical, and a reader who does not know that reads the first as an
all-clear.

## Proposed outcome

Someone who wants to know what an agent did on a machine — theirs, or one they
reach over SSH — can ask, in one command, and get an answer they can act on.

- `ai-mirror audit` prints the recent entries, readable without `jq`
- an empty result says **which** empty it is: nothing recorded, or a log that
  began at a boot after the thing being asked about
- the scope of the answer is stated, so "nothing since 09:14" is never
  mistaken for "nothing, ever"
- it works unchanged over SSH, because it reads a file and prints to stdout

## Affected users and systems

- anyone who has granted an agent control and later wants to know what it did
- anyone driving a machine remotely, where this is the only visibility there is
- `src/ai_mirror/cli.py`, `api.py` and `mcp.py` — AGENTS.md's recipe is
  "`api.run` branch + `mcp.TOOLS` entry + CLI subcommand + test", and whether
  all four apply is an open question below
- `tests/`, which cannot reach the desktop and does not need to: this is a read

## Constraints

**Read-only, and it must stay that way.** This verb answers a question about
trust. Anything that could write, clear or rotate the log belongs nowhere near
it — a log an agent can truncate is worse than no log, because it reads as
evidence.

**No new dependencies.** Stdlib Python, JSON in and out, as AGENTS.md says.
Boot time is available from `/proc`; nothing here needs a library.

**Do not claim more than the log supports.** AGENTS.md is explicit that the
gate is unforgeable only against an agent confined to MCP, and that machinery
claiming more must not be added. The same applies to wording: this shows what
was *recorded*, and an agent with a shell can act without a record if it
avoids the paths that call `audit()`.

**Must not become an exfiltration surface.** The log is 0600 for a reason. A
verb is fine; a verb that an MCP tool exposes to the agent being audited needs
a reason, and that is the open question below.

**An empty answer must not read as a clean one.** This is the whole of the
second half of the outcome.

## Open questions

1. **Should this be an MCP tool as well as a CLI verb?** AGENTS.md's recipe
   says a new tool is all four. But an agent reading its own audit trail is
   not obviously something to offer, and the reader this exists for is a
   person. CLI-only may be the right departure from the recipe — and if so,
   worth saying in AGENTS.md so the next person does not read it as an
   omission.

2. **How far back, and how much?** The log is per-boot so it cannot grow
   without bound, but a long session could still be thousands of lines.
   A default of the last N with `-n` to change it, or everything and let the
   caller pipe it?

3. **What does it print?** One line per event, human-first, with `--json`
   passing the raw lines through for a caller that wants them. Or JSON as the
   default, matching "JSON in/out" as the house style — which is about the
   MCP surface rather than about what a person reads.

4. **Does `status` already want this?** `status` reports the current owner. A
   reader asking "what happened" will try `status` first, and it could name
   the audit verb rather than leaving them to find it. Small, and it decides
   whether this is discoverable or just present.
