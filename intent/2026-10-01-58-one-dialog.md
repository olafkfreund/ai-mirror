# Intent: One confirm dialog, however many bars

## Problem

The confirm dialog is declared inside `plugin/Widget.qml`, the bar widget,
and the shell creates one bar widget per bar: one per monitor. On a
three-monitor host, one control request therefore opens three dialogs.

- Each dialog binds itself to the *focused* monitor, so the three stack in
  the same place.
- Each claims exclusive keyboard focus.
- Each runs its own copy of #48's state: the one-second timer, the pointer
  arming and the key handler.
- Each can answer the request through its own process.

Measured on p620:
- `shell.json` places the widget once;
- there are three monitors, and `hyprctl layers` shows three bar layers;
- Quickshell logs every open and close of `omarchy-ai-mirror-confirm`
  three times.

The dialog is the human's half of the control gate, and everything about it
assumes there is one. Today:
- keys go to whichever instance Hyprland gives focus;
- pointer arming goes to whichever is on top;
- up to three answers can race.

That makes the gate hard to reason about. It also makes an incident like
#57's two no-input grants harder to trace.

## Proposed outcome

A pending request shows exactly one dialog, on the focused monitor, on any
number of monitors. A request is answered at most once by the dialog. The
bar widget itself (the mark, the tooltip, click to stop) still appears on
every bar, as now.

## Affected users and systems

- Everyone with more than one monitor, which is every host this runs on
  today.
- `plugin/` only: `manifest.json`, `Widget.qml`, a new overlay entry point,
  and possibly where `AgentCommand` lives. No Python, CLI or MCP change.

## Constraints

- **Must not weaken #48:** the per-request reset, the one-second grace, the
  pointer arming and auto-repeat handling all carry over unchanged.
- The plugin directory contains no symlinks, and must pass Nixarchy's
  validator, which `nix flake check` mirrors.
- **Stacked on #48:** this changes #48's dialog, so #48 merges first.
- **The kill switch and the stop click must keep working from every bar.**

## Open questions

1. **How do we get one instance?**
   - (a) Declare an `overlay` entry point in `manifest.json`, which the
     shell creates once, and move the dialog there. This is what omapilot
     does (`"kinds": ["bar-widget", "overlay"]`, `entryPoints.overlay`).
   - (b) Keep the dialog in the widget, but let only one bar's instance
     create it, e.g. the bar on the primary monitor.

   Proposed: **(a).** It is the shell's own mechanism for one-per-shell UI,
   and the dialog stops depending on how many bars exist. (b) needs a rule
   for "which bar", which breaks when that monitor is unplugged. **Decided: as proposed.**
2. **Does an overlay entry point need anything the shell's version may not
   support?** To be checked in the spec against the installed Omarchy shell
   and its plugin validator, not assumed from omapilot. **Decided: as proposed.**
