# Intent: accessibility is switched on with the wrong property, and we document the opposite of what happens

## Problem

Two faults that compound each other: we throw the wrong switch, and then tell
agents the switch worked.

`enable_bus()` sets `org.a11y.Status IsEnabled` and nothing else. That interface
carries two writable properties, and on this desktop the one we set produces an
accessibility tree with no content in it — 24 nodes, maximum depth 1, roles only
`frame` and `application`. Asking for anything actionable returns nothing:
`a11y-find` for `push button`, `link` and `entry` are all empty. The tell is that
a depth-64 walk costs the same as a depth-1 walk, because there is no depth to
walk.

Setting `ScreenReaderEnabled` as well demonstrably changes that for at least one
application class, with no restart: in a controlled A/B run twice, one application
went from absent to 129 nodes with buttons and links, while Chrome, Discord and
generic Electron did not move at all. So the property is not a cure — Chromium
documents a launch-time flag as its activation route — but it is a real switch we
are simply not throwing. We also discard the result of the call that sets it, so
failing to set it is silent.

The second fault is worse, because it is the one that reaches agents.
`src/ai_mirror/gotchas.md` states that "Electron and GTK applications do expose
full trees with bounds and actions". Discord is Electron and exposes two nodes.
`gotchas` is in `DEFAULT_SECTIONS`, so `index` — the call an agent makes to orient
itself on this host — serves that sentence as fact. An agent that believes it
reaches for `a11y_find`, gets an empty result, and has no way to tell "this
desktop does not expose trees" from "the element is not there". The honest failure
is a screen that reads as empty.

This is the concrete mechanism behind the caveat already recorded in
olafkfreund/nixarchy-voice#31, which says an accessibility tree "needs the desktop
to expose one first" without saying how one would.

## Proposed outcome

- An agent calling `index` learns that accessibility on this desktop is
  opportunistic, how to check whether it is available before relying on it, and
  what to do when it is not — rather than being told it will work.
- Whatever we can switch on from the session bus, we switch on, and a failure to
  do so is visible rather than silent.
- The difference between "this host exposes no tree" and "that element does not
  exist" is distinguishable by the caller.
- The claim in the shipped documentation matches what this desktop actually does,
  and says how it was checked so the next person can re-check it.

## Affected users and systems

- Every agent using `a11y_tree`, `a11y_find` and `a11y_act`, and every agent
  reading `index` to orient itself.
- `src/ai_mirror/a11y.py` (`enable_bus`), `src/ai_mirror/gotchas.md`, and
  `src/ai_mirror/index.py` only insofar as it serves the gotchas section.
- The human's own desktop session, if a property we set has a cost in every
  toolkit application that honours it. This is the part needing the most care.
- olafkfreund/nixarchy-voice#31 depends on the answer here.

## Constraints

- Must not rewrite `intent/2026-09-17-3-desktop-index.md` or
  `spec/2026-09-17-3-desktop-index.md`. Both repeat the same false sentence, but
  they are approved artefacts recording what was believed at the time. Only the
  shipped `gotchas.md` describes the present and should change.
- Must not degrade the human's interactive desktop to make the agent's job
  easier. Accessibility has a cost in applications that honour it, and the human
  is using this machine.
- Must not relaunch or restart the human's running applications.
- Whatever replaces the false claim must be checkable. A corrected sentence that
  is merely asserted is the same failure again with a different value.
- `index` is read on every orientation, so anything added there earns its length.

## Open questions

1. Should `ScreenReaderEnabled` be set permanently, or only for the duration of
   agent control? `control.py` already has exactly that lifecycle — `mode=agent`
   on, `off` off — and gating it there would keep the cost off the human's
   desktop when no agent is driving. It would also mean the first `a11y` call
   after taking control races the toolkits waking up.
2. Do we go further than the session bus? Chromium exposes trees with
   `--force-renderer-accessibility` at launch, which would mean influencing how
   Omarchy launches browsers and Electron applications. That is a much larger
   change and arguably belongs to a separate task; it needs an explicit yes or no
   here so the spec knows its boundary.
3. Should `a11y_find` returning nothing be distinguishable at the API level from
   "this desktop exposes no tree"? A caller cannot currently tell, and that
   ambiguity is what turns a missing tree into a confident wrong answer.
4. Is it in scope to measure the cost of enabling accessibility on this desktop,
   or do we accept it untested on the grounds that it is toggled with control?
