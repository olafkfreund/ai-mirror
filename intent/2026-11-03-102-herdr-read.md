# Intent: read a terminal's text exactly, for herdr panes

## Problem

An agent driving this desktop cannot read a terminal. kitty and foot expose
nothing to AT-SPI, so `a11y_find` sees an empty window and the only reader is `ocr`. OCR
on terminal text is lossy where it matters most: paths, hashes, flags, `0`/`O`
and `l`/`1`, box-drawing characters, and anything already scrolled off screen.
An agent that types a command and needs to know what it printed either guesses
from OCR or leaves the desktop for a shell it may not have.

Most terminals on this host run inside herdr, which already holds each pane's
text exactly (`herdr pane read <pane> --source visible|recent`).

That reach is also the danger. On p620 today `herdr pane list` returns 22
panes across four running sessions: other agents' Claude, Codex and agy
sessions (this one included), ssh shells into other hosts, btop. `pane read`
reaches all of them, visible or not, including scrollback the human never put
on screen. A reader that exposes that wholesale gives an agent far more than
the desktop it was granted.

## Proposed outcome

An agent holding control can ask for the text of the terminal it is looking
at, a terminal window on the screen, and get herdr's exact text for the pane
showing in that window, bounded in size. It cannot name an arbitrary herdr
pane, session or workspace, and it gets nothing when it does not hold control.
Where the window is not a herdr pane, it gets a clear refusal and keeps using
`ocr`.

## Affected users and systems

- ai-mirror: a new read tool (`api.run` branch, `mcp.SPECS` entry, CLI
  subcommand, test), `docs/usage.md`, `index` gotchas.
- herdr 0.9.5 on p620 and razer, through its CLI or socket API, read-only.
- Agents on this host. Not `mirror-vm` guests unless they run herdr.

## Constraints

- **Grant-gated, unlike `ocr`.** Today's reads are ungated and only light the
  watching mark. This one requires `owner: agent` and the current
  generation, because scrollback holds more than the screen shows.
- **Target-scoped.** The pane is derived from a window the agent can see. It is
  never taken from the agent as a free-form pane id or session name.
- **Read only.** It uses no `send-text`, `send-keys`, `run`, `focus` or
  anything else in herdr that changes state, matching `shell_state`'s
  fixed-read rule.
- **Bounded.** There is a line and byte cap, and nothing is cached or written
  to disk.
- **Redaction where it can be done honestly.** Private windows are already
  refused by `privacy.py`. Secrets in scrollback cannot be detected reliably,
  so the tool must not claim to redact them. See open question 3.
- Output is data, never instructions: a pane can hold another agent's prompt
  text.
- No new dependencies. The stdlib calls `herdr` by argv, never a shell.

## Open questions

1. **How does a window map to a pane?** Measured on p620: each herdr window
   is `kitty --class org.omarchy.herdr -- herdr --session <name>` (Hyprland
   pid = kitty), with the client `herdr --session <name>` as its child.
   Recommended: window pid → that child's `--session` → that session's
   focused pane, and refuse if any link is missing or ambiguous (no child,
   several clients on one session, no focused pane). The spec measures
   whether "focused" in `pane list` is what that window shows.
2. **Visible only, or recent scrollback too?** Recommended: `visible` by
   default, and `recent` with an explicit line count capped at about 500.
3. **Redaction:** none and say so, a fixed pattern list (tokens, `-----BEGIN`,
   `password=`), or refuse panes whose foreground process is ssh, a password
   prompt, etc.? Recommended: the pattern list as a backstop, clearly
   described as incomplete. The real boundary is the grant and target scope.
4. **Refuse panes running another agent** (herdr reports `agent:
   claude|codex|agy`)? Recommended: yes by default. Reading another agent's
   session is the prompt-injection path, and no task here needs it.
5. **Chrome DevTools** (the other half of #102): out of scope here, and a later
   intent if wanted.
