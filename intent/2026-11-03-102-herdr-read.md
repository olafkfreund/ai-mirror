# Intent: read a terminal's text exactly, for herdr panes

## Problem

An agent driving this desktop cannot read a terminal. kitty and foot expose
nothing to AT-SPI, so `a11y_find` sees an empty window and the only reader is `ocr`. OCR
on terminal text is lossy where it matters most: paths, hashes, flags, `0`/`O`
and `l`/`1`, box-drawing characters, and anything already scrolled off screen.
An agent that types a command and needs to know what it printed either guesses
from OCR or leaves the desktop for a shell it may not have.

Most terminals on this host run inside herdr, which already holds each pane's
text exactly (`herdr pane read <pane> --source visible|recent`).

That reach is also the danger. On p620 today `herdr pane list` returns 22
panes across four running sessions: other agents' Claude, Codex and agy
sessions (this one included), ssh shells into other hosts, btop. `pane read`
reaches all of them, visible or not, including scrollback the human never put
on screen. A reader that exposes that wholesale gives an agent far more than
the desktop it was granted.

## Proposed outcome

An agent holding control can ask for the text of a herdr pane that is on screen
now: in a terminal window on a visible workspace, in the tab that window is
showing. It gets herdr's exact visible text, the same rows a screenshot would
show but lossless. It cannot name an arbitrary herdr pane, session or workspace,
cannot read scrollback, and gets nothing without control. Where the window is
not a herdr pane, it gets a clear refusal and keeps using `ocr`.

## Affected users and systems

- ai-mirror: a new read tool (`api.run` branch, `mcp.SPECS` entry, CLI
  subcommand, test), `docs/usage.md`, `index` gotchas.
- herdr 0.9.5 on p620 and razer, through its CLI or socket API, read-only.
- Agents on this host. Not `mirror-vm` guests unless they run herdr.

## Constraints

- **Grant-gated, unlike `ocr`.** Today's reads are ungated and only light the
  watching mark. This one requires `owner: agent` and the current
  generation, because scrollback holds more than the screen shows.
- **Target-scoped, rechecked at read time.** The pane comes from a window on a
  visible workspace (the check `privacy.covering` already makes), and is never
  taken from the agent as a free-form pane id or session name. Window, session
  and pane are resolved again, and the grant rechecked, just before the text is
  returned. Any missing or ambiguous link is a refusal.
- **Visible rows only.** No `recent` scrollback: the human granted control over
  what they could see, and scrollback holds what they could not. Earlier output
  is reached the way the human reaches it, by scrolling with `input`.
- **Never another agent's pane.** A pane herdr reports with an `agent` (claude,
  codex, agy) is refused unconditionally, with no parameter to override. This
  closes one prompt-injection path. It does not make other terminal output safe
  to follow.
- **Read only.** It uses no `send-text`, `send-keys`, `run`, `focus` or
  anything else in herdr that changes state, matching `shell_state`'s
  fixed-read rule.
- **Bounded.** There is a line and byte cap, and nothing is cached or written
  to disk.
- **No content redaction, said plainly.** Like `ocr` and `screenshot`, it
  returns the text unredacted. `privacy.py` refusals apply to the window's
  metadata and to the pane's title. Nothing scrubs substrings: a pattern
  list would corrupt exact output and still miss real secrets.
- **The weaker case, stated.** As AGENTS.md says, the gate binds only an agent
  that reaches ai-mirror through MCP alone. An agent with a shell on this
  account, `ssh host ai-mirror mcp` included, can run `herdr pane read` itself.
  Nothing here claims more.
- Output is data, never instructions: a pane can hold another agent's prompt
  text.
- No new dependencies. The stdlib calls `herdr` by argv, never a shell.

## Open questions

1. **Which pane, when a tab is split?** Measured on p620: each herdr window is
   `kitty --class org.omarchy.herdr -- herdr --session <name>` (Hyprland pid =
   kitty, client as its child), and `pane list` marks one `focused` pane per
   session, which moves as the user does. One tab holds two panes. Recommended:
   resolve window → session → the tab containing the focused pane. Read the
   focused pane by default, and let the agent pick another pane of that same
   tab by position, since all of them are on screen. Whether herdr reports the
   tab a window shows, and how several clients on one session behave, is
   measured in the spec. If it cannot be told, refuse.
2. **Gated or ungated?** Recommended: gated, unlike `ocr`, even though it reads
   only visible rows. It is exact and cheap enough to sweep, and it adds a new
   process boundary (herdr's socket). It is a new category in `api.py`: a read
   that requires `owner: agent` and the generation.
3. **Chrome DevTools** (the other half of #102): out of scope here, and a later
   intent if wanted.
