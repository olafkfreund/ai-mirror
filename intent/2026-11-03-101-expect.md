# Intent: confirm that an action changed something

## Problem

`input`, `window` and `launch` report delivery, not effect: `input` returned
164 ms before the panel it opened existed. Today the agent follows up with
`wait`. That works for a state that did not hold before the action, but `wait`
cannot tell "my action did this" from "it was already like this":

- the layer was already mapped, so `wait --layer` confirms at once and the
  keypress that may have closed it goes unnoticed;
- a window of that class already existed, so `wait --window-class` confirms on
  the old one;
- "the title changed" or "this window closed" cannot be asked at all without
  knowing the state before the action. The agent can only read that state
  separately, one round trip earlier, and races anything that changes in between.

The extra round trip itself is a smaller cost: it is dead air on a recording,
and in a `mirror-vm` batch it is one more step.

## Proposed outcome

A mutating call can carry one `expect` predicate. ai-mirror reads the relevant
state just before acting, acts, then polls until the state has **changed to**
what was expected, or until a deadline. The result keeps `wait`'s three answers:
`confirmed`, `not_confirmed` (never a reason to retry), and `unavailable`.
Without `expect`, every call behaves as it does now.

## Affected users and systems

- `src/ai_mirror/{mcp,api,wait}.py`, the CLI and `docs/usage.md`.
- Agents on the host, and in the VM through `mirror-vm`.
- No change to the ownership gate or to `run_batch`.

## Constraints

- It never retries or repeats the action. `not_confirmed` stays information,
  as in `wait`.
- A state that already held before the action is `not_confirmed` for "appeared"
  predicates, not `confirmed`. That case is the reason this exists.
- It adds no new way to cause effects: `expect` only reads, and only after the
  action is sent.
- It uses the same reads as `wait` (hyprctl, about 10 ms) and adds no dependencies.
- The deadline is bounded like `wait`'s (30 s at most). The call's result
  carries both the action's result and the expectation's.

## Open questions

1. **Which tools?** Recommended: `input`, `window` and `launch`. `a11y_act` and
   clipboard can wait.
2. **Which predicates?** Recommended: `wait`'s set (layer, window class, window
   title, workspace, monitor, layout, each with `absent`) plus two changes that
   only make sense with a before-state:
   - "focused window changed";
   - "this window's title changed".
   Rejected: a visual-settle frame hash. It costs a full capture per poll, and a
   blinking cursor or a clock never settles.
3. **Events or polling?** Recommended: polling, as in `wait`. The #95 event ring
   exists only in the MCP server and only while it holds a grant, so the CLI and
   tests would need a second path. Polling at 50 ms is fast enough here.
