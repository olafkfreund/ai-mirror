# Intent: there is no dev environment, and the tests that need a desktop run against the human's own

## Problem

Two costs, both paid while implementing #12, and neither is a one-off.

**Getting a working environment is undocumented reverse engineering.**
`tests/test_invariants.py` imports `ai_mirror.a11y`, which needs PyGObject and
the `at-spi2-core` typelib. The flake wrapper provides both, but only for the
built package — there is no `devenv.nix`, no `shell.nix`, no `devShells` output.
A plain `PYTHONPATH=src python3 -m unittest` fails with `AT-SPI bindings missing
(Namespace Atspi not available)`. What worked was stripping the `exec` line out
of `result/bin/ai-mirror`, appending a different `PYTHONPATH`, and running
through that shim. It is a fine trick and nobody should have to find it twice.

**The tests that most need a desktop are the ones we cannot safely run against
one.** #12 put accessibility enablement behind the control gate. `ControlTests`
already takes control, so without a stub every one of those tests would have
written `org.a11y.Status` on the developer's live session bus. That was caught by
review; 584d8ee fixed the same shape of bug for the desktop before it. Twice is a
pattern, and it recurs because the safe path is opt-in while the unsafe path is
what the code does by default.

The things that genuinely need a compositor are not covered at all: the
virtual-keyboard and virtual-pointer helper against a real Wayland session, #11's
confirm dialog and the kill switch, and whether enabling accessibility costs
anything.

That last one did not merely go untested — it **failed**. #12's plan required the
enablement cost be measured and recorded whatever it showed. Two paired 40 s
rounds of Chrome and Discord CPU disagreed with each other, because the desktop
was in use: Chrome sat near 72% of a core with video playing, and the first
round's apparent cost did not reproduce when the order was reversed. So the plan
records "no measurable cost" and marks the decision that reasoning no longer
supports. A quiet machine with a known set of applications would have answered it
in one round. The same gap blocks #13, which needs a browser relaunched with a
flag — not something to do to somebody's own session.

## Proposed outcome

- Entering the project gives a working environment, without reading the flake
  wrapper to reconstruct one.
- The suite can run against a real Hyprland session in a throwaway machine, so a
  test that reaches the human's desktop is structurally impossible rather than
  caught by whoever reviews it.
- The a11y cost question #12 left open is answerable, and #13 is testable.
- A contributor who has never heard of nixarchy can still read the environment
  file and work out what it does.

## Affected users and systems

- Anyone developing or reviewing this repository.
- `tests/`, and whatever file ends up describing the environment. No change to
  `src/` behaviour is sought by this intent.
- The developer's own desktop session, which is what the current arrangement puts
  at risk.
- nixarchy's existing VMs, used as they are. This intent proposes **no new VM**:
  `nix run .#vm` is already stateless by design so every boot is a clean install,
  `.#vm-big` is already persistent with ssh on 2224, and the display backend is
  deliberately unpinned (`vm/configuration.nix:128`) so both work headless and
  over ssh. olafkfreund/nixarchy#817 already records that `vm-big` is the one
  kept for development, and warns in as many words that an agent reading only
  `.#vm` would "build a third one".

## Constraints

- **The environment file is the project's, and speaks its own tool's vocabulary.**
  No nixarchy option, helper or import may appear in it. A teammate who has never
  used this machine must be able to read and edit it from the tool's reference
  alone.
- **No machine change is in scope.** `devenv` is installed here (2.3.1) but
  `programs.nixarchy.services.devenv` is not enabled, so there is no shell hook
  and `nixarchy dev` cannot drive it. Until somebody enables that — a rebuild,
  and a decision for the machine's owner — activation is a command typed by hand.
  This intent must produce something that works anyway.
- **No credential may appear in the environment file.** It is committed, and it is
  world-readable in the Nix store besides.
- **The VM path must not become the only path.** The suite has to keep running in
  the nix sandbox, where there is no compositor and no session bus, or
  `nix flake check` stops being the gate.
- **Must not slow the ordinary loop.** Booting a VM to run 73 unit tests that
  pass in 2.7 seconds would be a worse environment than none.
- p620 carries all four nixarchy CI runners, so anything that ends up rebuilding
  the machine has to be announced and timed against jobs in flight.

## Open questions

1. **What is the split between the two ways of running the suite?** The obvious
   line is that everything mockable stays fast and local, and only what genuinely
   needs a compositor goes to the VM. But #12's near-miss argues the opposite for
   safety: if the local path can still reach a real bus when someone forgets a
   stub, it is the default that is wrong, not the forgetting.
2. **Which VM, and does this repository own its lifecycle?** `.#vm` is clean per
   boot and slow to start; `.#vm-big` is warm and persistent but shared with
   other work and is olafkfreund/nixarchy#817's subject. Booting one per test run
   and booting one per day are different designs.
3. **Does the VM need this repository's own build inside it, and how does it get
   there?** Testing the packaged `ai-mirror` and testing the working tree are
   different questions, and the second one needs the source across the boundary.
4. **Is the a11y cost measurement (#12 step 7) part of this task or its own?**
   It is the concrete thing that failed, so it is the obvious first user — but it
   is also a measurement task rather than an environment one.
