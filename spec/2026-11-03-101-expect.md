# Spec: confirm that an input changed something

## Design

### Where

Only on `input`: an optional argument `confirm`, exposed in the MCP schema, the
CLI `input --confirm '<json>'` and `api.run`. The intent named `window` and
`launch` too, but both already confirm their own effect:
- `launch` polls for the new window and returns it, or a note.
- `window` checks the compositor and returns `verified` or `not_confirmed`.

So the field would add nothing there.

The name is `confirm`, not `expect`: `a11y_act` already has `expect` for a
precondition on the element. Reusing it for an outcome would make one word
mean two things. `confirm` also matches the `confirmed` result.

### Shape

`confirm` is an object holding exactly one predicate plus an optional `timeout`:

| Predicate | Before the batch | Confirmed when |
|---|---|---|
| `layer`, `window_class`, `window_title`, `workspace`, `monitor`, `layout` (from `wait.PREDICATES`), with `absent` | the predicate's bool | it is `not absent` now **and** it was not so before |
| `focus_changed: true` | `activewindow` address | the address differs |
| `title_changed: "<address>"` | that window's title | the title differs, or the window is gone |

The timeout defaults to 3 s and is capped at 30 s, through `wait._timeout`.
Validation: exactly one predicate, and the same messages as `wait`. Bad
`confirm` input raises `ValueError` **before** anything is sent.

### Flow, in `api.run`'s `input` branch

1. Validate `confirm`.
2. Read the before-state. If that read fails, remember it and still send the
   batch: `confirm` never changes whether the action runs.
3. Run `control.run_batch`, as today. If it raises, that error is the result
   and nothing is polled.
4. Call `wait.poll(...)` with the "changed" check. If the before-state could not
   be read, the result is `unavailable` with the reason.
5. Add the result under `confirm` in the input result:
   `{result, polls, predicate, waited_ms[, reason][, held_before: true]}`.

`held_before: true` with `not_confirmed` covers a state that already held
before the action, which is the intent's central case. The answers stay three,
and the reason is explicit.

The MCP `screenshot=true` capture happens after `api.run` returns, so after
`confirm`. That is correct: the screenshot shows the confirmed state.

### Code

- `wait.py`:
  - add `_focus` (`activewindow` → address) and `_title_of(address)` (from
    `clients`, `None` if gone);
  - add `confirm(spec)` → `(before_fn, check_fn)` built on the existing
    `PREDICATES`;
  - reuse `poll`.

  `until` is unchanged.
- `api.py`: steps 1 to 5 above, about 10 lines.
- `mcp.py`: `confirm: {'type': 'object'}` on `input`, plus one sentence in the
  description.
- `cli.py`: `--confirm` JSON.
- `docs/usage.md`: one row.
- `gotchas.md` is unchanged.

## Alternatives rejected

- **`expect` on `window` and `launch`:** both already confirm (see Where).
- **The name `expect`:** it already means a precondition in `a11y_act`.
- **A visual-settle frame hash:** a full capture per poll, and a cursor or a
  clock never settles (agreed in the intent).
- **Events from the #95 ring:** only in the MCP server and only while it holds
  a grant. The CLI and tests would need a second path (agreed in the intent).
- **Refusing to act when the before-read fails:** that would make a
  confirmation option change whether input is delivered. The answer
  `unavailable` says the same thing without that side effect.
- **Retrying on `not_confirmed`:** ruled out by the intent.

## Risks

- **A state caused by something else:** a matching state can have another
  cause, such as a notification layer or another window. It is documented, as
  for `wait`, and `confirmed` is not proof that the input caused it.
- **Delay:** a slow app adds up to `timeout` to the call. Nothing is held during
  the poll: `run_batch` has returned, and the helper is idle.
- **Both hosts:** this is read-only `hyprctl` after the action. There is no
  change to the gate or to `run_batch`. p620 and razer get it through the
  normal nixarchy bump.

## Verification

- Unit tests (`Base`, with `host.ctl` and `control.run_batch` stubbed):
  - each predicate kind confirms on a change;
  - `held_before` when it already held;
  - `absent`;
  - `focus_changed`;
  - `title_changed` for a changed title and for a closed window;
  - a failed before-read → `unavailable`, and the batch is still sent;
  - a `run_batch` error → no poll;
  - invalid `confirm` → `ValueError` with nothing sent;
  - no `confirm` → result unchanged;
  - the CLI parses `--confirm`.
- `nix flake check` and `nix build .#ai-mirror`.
- Live on p620, with the checkout CLI and a grant:
  - the key that opens a panel, with `confirm {layer: <ns>}`, gives `confirmed`;
  - the same again while it is open gives `not_confirmed` with `held_before`;
  - typing into foot with `confirm {title_changed: <addr>}` after a command
    that sets the title.
