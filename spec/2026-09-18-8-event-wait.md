# Spec: Bounded confirmation that a prerequisite holds

## The intent's open questions, answered

1. **State polling, not events.** Measured on p620: every prerequisite the
   intent names is already a state query, and each costs about 10 ms.

   ```
   hyprctl layers -j           0.01s   panel present by namespace
   hyprctl clients -j          0.01s   window exists
   hyprctl activeworkspace -j  0.01s   workspace and monitor
   hyprctl devices -j          0.01s   active_keymap per keyboard
   ```

   Events buy nothing here and cost a subscription, a lifetime and a race. The
   event socket stays unused; if a future prerequisite is genuinely transient,
   that is when it earns its place.

2. **A separate `wait` operation, checked after the action.** This follows from
   1 rather than being an independent choice: a state that persists can be
   observed after the fact, so there is no ordering race to close and no reason
   to couple this to `input`. The arm-act-await token design solves a problem
   this design does not have.

3. **No control grant.** `wait` observes and mutates nothing, like `index`. It
   does not need to police revocation either: a caller whose control was
   revoked fails on its next `input` with `not_owner`, which is the existing
   and correct signal.

4. **A batch is untouched.** `wait` is its own operation, so `input`'s action
   list keeps today's semantics exactly. Whether to stop is the caller's
   decision, taken on a result it can actually see.

5. **Named predicates only.** The caller nominates what it expects and gets
   back whether it held. No client lists, no window titles, no raw events --
   which also settles the privacy point, since the result is a boolean and a
   duration rather than an inventory of what the user has open.

6. **Worth building, on ergonomics.** A caller could run `hyprctl layers`
   itself; the capability is not new. What is new is that the check is one call
   with a bounded loop and four distinguishable outcomes, instead of each
   caller writing its own poll and getting the timeout semantics wrong. The
   claim is that a check nobody has to write is a check that actually gets
   used. If that is not persuasive, this should not be built.

## Design

One operation, `wait`, in `api.run` beside the other read-only ones. No new
module state, no threads, no sockets, no cache.

### The call

```
ai-mirror wait --layer nixarchy-pkg-menu --timeout 3
ai-mirror wait --window-class Google-chrome
ai-mirror wait --layer nixarchy-pkg-menu --absent      # wait for it to close
```

MCP: `wait` with `{until: {...}, timeout, absent}`.

### Predicates

Exactly one per call. More than one invites "which failed?" and the caller can
make two calls.

| Predicate | Holds when | Source |
|---|---|---|
| `layer` | a layer surface has that namespace | `hyprctl layers -j` |
| `window_class` | a client has that class | `hyprctl clients -j` |
| `window_title` | a client's title contains that substring | `hyprctl clients -j` |
| `workspace` | the active workspace has that id | `hyprctl activeworkspace -j` |
| `monitor` | that monitor is focused | `host.monitors()` |
| `layout` | every keyboard reports that `active_keymap` | `hyprctl devices -j` |

`absent: true` inverts the predicate, which is how a caller waits for a panel to
close before opening the next one -- the sequencing mistake that stacked panels
during the session behind #3.

### The loop

Check once immediately, then every 50 ms until the deadline. The immediate
check is not an optimisation: a prerequisite that already holds never
transitions, and an event-shaped design would wait out the full timeout on the
commonest case in the codebase.

Default timeout 3 s, maximum 30 s. At ~10 ms per poll against a 50 ms interval
the duty cycle is about a fifth of one core's `hyprctl` cost, and the common
case returns in one or two polls.

### The result

```json
{"result": "confirmed", "waited_ms": 210, "polls": 5}
{"result": "not_confirmed", "waited_ms": 3000, "polls": 60}
{"result": "unavailable", "reason": "Hyprland: ..."}
```

Three outcomes, not the intent's four: `cancelled` has no meaning in a
synchronous call the caller can simply stop waiting on, and inventing a state
that cannot occur would be worse than omitting it.

`not_confirmed` deliberately does not say the action failed. The docstring and
the tool description both say so, because the whole point is that a caller
retrying on it can toggle shut a panel that had just opened.

`unavailable` is separate from `not_confirmed` for the same reason: "I could
not look" and "I looked and it was not there" are different facts, and a caller
that conflates them will act on the absence of evidence.

## Alternatives rejected

- **Waiting on the event socket.** The primitive the first draft assumed, and
  the reason this spec exists in this shape. It loses to polling on every axis
  that matters here: it cannot see a prerequisite that already holds, it needs
  a subscription established before the action, an event proves a transition
  rather than the state the caller depends on, and it cannot attribute that
  transition to this caller. Reconsider only for a genuinely transient
  prerequisite, which none of the six is.
- **`expect` as a field on `input`.** Closes an ordering race that polling does
  not have, and couples the largest tool schema here to a second concern.
- **Arm, act, then await a token.** Solves transience and causality, neither of
  which this design needs, at the cost of expiry, cleanup and lifetime bugs.
- **Multiple predicates per call.** Ambiguous failure, no expressive gain.
- **A configurable poll interval.** A knob nobody can set well; 50 ms against a
  10 ms probe is not a number a caller should have to think about.
- **Returning the matched object** (the client, the layer). Useful for
  debugging, and it turns a boolean into an inventory of what the user has
  open. `windows` already exists for callers that want that.

## Risks

- **A confirmed prerequisite can stop holding** before the next action. This
  narrows a window rather than closing one, and the tool description must not
  imply otherwise.
- **No causal attribution.** Another agent, or the human, can satisfy the
  predicate. On a machine that currently runs fifteen agent sessions this is
  not theoretical. It is inherent to observing state rather than causation, and
  is documented rather than solved.
- **Compositor version contract.** `layers`, `clients`, `devices` and
  `activeworkspace` are Hyprland's shapes, not ours, and 0.56 is what was
  measured. A rename upstream turns every wait into `unavailable` -- which is
  at least the honest failure, not a false negative.
- **A caller that ignores the result** is exactly as unsafe as today. This
  cannot be fixed here.
- **Polling cost under a long timeout.** Bounded by the 30 s maximum and the
  50 ms interval; the common case is one or two polls.

## Verification

- **Unit tests**, stdlib `unittest`, with `hyprctl` stubbed: each predicate
  holds and does not hold; `absent` inverts; an already-true prerequisite
  returns on the first poll with a small `waited_ms`; a never-true one returns
  `not_confirmed` at the deadline rather than raising; a failing `hyprctl`
  returns `unavailable` and never `not_confirmed`; an unknown predicate is
  rejected by name; timeout is clamped to the maximum.
- **A timing test** that a prerequisite becoming true part-way through is
  noticed within roughly one interval, not at the deadline.
- **Live smoke on this host**, the case that motivated the work: press
  `SUPER + ALT + N`, `wait --layer nixarchy-pkg-menu` confirms in well under a
  second, and `wait --layer nixarchy-pkg-menu --absent` confirms after
  `omarchy-shell hide`. Then the negative: `wait --layer does-not-exist`
  returns `not_confirmed` at its deadline.
- **`nix flake check`** and `python3 -m unittest discover -s tests` green.
- **Acceptance**: the panel-open step of the package sequence is driven with a
  `wait` between pressing the key and typing, and a deliberately wrong
  keybinding produces `not_confirmed` instead of a sequence typed into whatever
  had focus.
