# Spec: switch accessibility on properly, and say what it actually gives us

## The intent's open questions, answered

These are decisions for the approver. Each is argued from a constraint already
approved in the intent.

1. **`ScreenReaderEnabled` is set with agent control, not permanently.**
   The intent forbids degrading the human's desktop to make the agent's job
   easier. `control.set_owner` (`control.py:86`) already owns exactly this
   lifecycle. Setting it there costs the human nothing while no agent is driving.
2. **Session bus only. The Chromium launch flag is out of scope.**
   `--force-renderer-accessibility` means changing how Omarchy launches browsers,
   which is a different blast radius and a different repository. Filed as a
   follow-up, referenced from the corrected `gotchas.md` so the knowledge is not
   lost.
3. **Yes, an empty result becomes distinguishable from an absent tree.**
   This is the intent's headline failure — an agent cannot tell "not there" from
   "nothing is exposed" — and no other decision here fixes it.
4. **Yes, the cost is measured**, because decision 1 is justified by a cost we
   have not quantified. If it turns out to be negligible the gating is still
   correct, but the reasoning in this spec would be wrong and should be corrected.

## Design

### 1. `enable_bus()` sets both properties and reports failure

`a11y.py:29-31` sets `IsEnabled` alone and discards the result. It sets both
properties on `org.a11y.Status`, and a non-zero `busctl` exit becomes a visible
`unavailable` condition rather than silence. Both properties are writable and
`emits-change`, verified by `busctl --user introspect org.a11y.Bus /org/a11y/bus`.

It records what each property was **before** we changed it.

### 2. Enablement moves to the control gate, and happens once per process

Two changes, which together remove a subprocess from every a11y call:

- `control.set_owner('agent', …)` enables the bus. This also gives toolkits time
  to build their trees before the first `a11y_find`, which a per-call enable
  cannot do — by the time `_walk` has shelled out to `busctl`, it is already
  walking.
- `_walk` (`a11y.py:71-74`) currently calls `enable_bus()` on every invocation,
  so every `a11y_tree` and `a11y_find` pays a `busctl` subprocess with a 5 s
  timeout. It keeps its `enable` parameter and its meaning, but the call becomes
  idempotent per process via a module-level flag, so the cost is paid once.

`index.nav()`'s `enable=False` (`index.py:296-306`) keeps working unchanged:
orientation must still not turn anything on.

### 3. `set_owner('off', …)` restores only what we changed

If the human runs a real screen reader, `ScreenReaderEnabled` was already true
and is **not** touched on the way out. Restoration uses the values recorded in
decision 1, so we put back what was there rather than writing `false`
unconditionally. The recorded values live in the existing `state.json`
(`control.py:44-56`), which is already written atomically under a lock.

If a server dies without running its teardown, the property stays on. That is the
safe direction to fail — the desktop keeps working and the next `control off`
restores it.

### 4. `tree()` and `find()` report coverage

`find()` returns `{'nodes': matches}` (`a11y.py:117-127`) and nothing else, so an
empty list is ambiguous. Both gain a coverage summary drawn from the walk that
already happens: how many nodes were visited, and whether anything below the
application/frame level was seen at all.

That makes the two cases distinguishable by the caller:

- walked 153 nodes, no match → the element is not there.
- walked 24 nodes, none deeper than a frame → **this desktop is exposing no
  content tree**; use a screenshot, and do not conclude the screen is empty.

The wording of the second is part of this spec, because it is the sentence that
stops an agent drawing the wrong conclusion. No new walk and no new AT-SPI calls:
the counts come from the traversal already running.

### 5. `gotchas.md` describes this desktop and says how to check

`src/ai_mirror/gotchas.md:89` currently asserts:

> Electron and GTK applications do expose full trees with bounds and actions.

Replaced with what is true here, the command that checks it, and the fact that
enablement is per-application rather than global. It stays in the same section and
does not grow: `gotchas` is in `DEFAULT_SECTIONS` (`index.py:47`) and is read on
every orientation, so length is a cost paid every time.

Per the intent's constraints, `intent/2026-09-17-3-desktop-index.md:68` and
`spec/2026-09-17-3-desktop-index.md:98` are **not** touched.

## Alternatives rejected

- **Set `ScreenReaderEnabled` permanently at session start.** Simplest, and
  rejected by the intent's constraint against degrading the human's desktop. Every
  toolkit application that honours the property builds and maintains a tree for
  the whole session, for an agent that drives it a fraction of the time.
- **Write `false` on `control off` unconditionally.** One line shorter and it
  silently disables a real screen reader. Not acceptable at any saving.
- **Relaunch applications with `--force-renderer-accessibility` when control is
  taken.** Would genuinely fix Chrome and Electron, and is forbidden by the
  intent's constraint against restarting the human's running applications.
- **Return a bare `available: false` flag instead of coverage counts.** Cheaper,
  but it cannot distinguish "no tree" from "tree present, nothing matched", which
  is the whole point of decision 3.
- **Probe with a dedicated "is a tree available" call.** A second walk to learn
  what the first walk already knew.
- **Drop AT-SPI and commit to OCR.** Rejected because where a tree does exist it
  is exact text rather than a 67%-overlap guess, and because
  olafkfreund/nixarchy-voice#31 depends on this path existing.

## Risks

- **A human screen-reader user is switched off by our teardown.** The worst
  outcome here, and the reason for decision 3. Mitigated by restoring recorded
  values rather than writing `false`; covered by a test that asserts a
  pre-existing `true` survives an `agent` → `off` cycle.
- **Moving enablement to the control gate changes bare-CLI behaviour.** A human
  running `ai-mirror a11y-tree` with control off currently enables the bus as a
  side effect. Keeping `_walk`'s `enable` parameter preserves that; the per-process
  flag changes only how often it is paid.
- **Toolkits wake asynchronously.** Enabling at `control agent` and calling
  `a11y_find` immediately may still race an application that has not built its
  tree. Decision 1 shortens this window rather than closing it, and the coverage
  report in decision 4 makes the race legible instead of silent.
- **`busctl` is absent or the a11y bus is down.** Already in `doctor`'s required
  set (`api.py:16-21`); surfacing the failure is an improvement on today's silence.
- **The measured cost may contradict decision 1.** Stated as a risk rather than
  hidden: if enabling accessibility proves free, the gating is harmless but this
  spec's reasoning is wrong and should be amended, not quietly kept.

## Verification

**Unit.** `enable_bus()` issues both property writes and raises on a non-zero
exit. `set_owner('off')` restores a recorded `true` rather than writing `false`.
Coverage counts are computed without additional AT-SPI calls. `index.nav()` still
enables nothing.

**Runtime, on this host.** The A/B that produced the issue, as a repeatable
procedure: record both properties, take a per-application node census with
`a11y-tree --depth 64 --max-nodes 4000`, take control, re-census, drop control,
confirm both properties are back to their recorded values. The expected result is
the table in #12 — one application gaining content, Chrome and Discord unchanged.

**Coverage wording.** With the tree unavailable, `a11y_find --role 'push button'`
must return a result an agent can act on correctly, naming the desktop rather than
the element. Checked by reading it, not only by asserting a field exists.

**Cost (decision 4).** CPU time of the Chrome and Discord process trees over a
fixed idle interval with the property off, then on, same workload. Recorded in the
plan whatever it shows, including if it shows nothing.

**Not verified here.** Whether other hosts behave as this one does. Every number
in #12 is from this desktop, and the corrected `gotchas.md` says so rather than
generalising the way the sentence it replaces did.
