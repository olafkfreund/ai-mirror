# Spec: an environment you enter, and a default that cannot reach your desktop

## The intent's open questions, answered

Decisions for the approver. Question 1 is the one most worth overruling if you
disagree, because it chooses a philosophy rather than a mechanism.

1. **The split is not by speed. The local default stops being able to touch the
   desktop at all.** The intent put the two readings side by side: split
   mockable-and-fast from compositor-and-slow, or treat the default as the bug.
   The evidence decides it. Twice now a test has been one forgotten stub away
   from the developer's own session — #12's control gate, and 584d8ee before it.
   Both were caught by a person reading a diff. A third will not be. So the
   side-effecting seams refuse to act while the suite is running, and a
   forgotten stub becomes a **test error** rather than a write to somebody's
   desktop. Speed then splits itself: everything that can be answered without a
   compositor already runs in 2.7 s and stays there.
2. **Neither VM, for the automated suite — a `nixosTest`.** `.#vm` and
   `.#vm-big` are for a human at a console. An automated test wants no
   lifecycle to manage, no ssh, no port, no teardown, and it wants to run inside
   `nix flake check`. nixpkgs already tests wlroots compositors exactly this way;
   `nixos/tests/sway.nix` runs one headless under software rendering
   (`WLR_RENDERER = "pixman"`). `.#vm` headless keeps its place for
   **interactive** work — the measurement #12 step 7 could not do, and #13's
   browser flag — but this repository owns no VM's lifecycle.
3. **The source crosses by Nix, not by ssh.** A `nixosTest` builds the flake's
   own package into the guest. There is no share to mount, no rsync, no copy
   step, and no way for the guest to be testing a different tree than the one in
   front of you.
4. **The a11y cost measurement is its own task.** It is the thing that failed,
   so it is the obvious first user of this — but it is a measurement, not an
   environment, and folding it in here would let a hard measurement hold up a
   `devenv.nix` that is useful on its own.

## Design

### 1. `devenv.nix` — the environment a contributor enters

Python with the project's own interpreter, `at-spi2-core`'s typelib and
PyGObject on it, and the C helper's build inputs. Scripts for the two things
anyone actually runs: the suite, and the suite plus the checks.

It is written in devenv's vocabulary and nothing else — no nixarchy option, no
helper from this machine, no import of ours. Someone who has never heard of
nixarchy must be able to read it against
<https://devenv.sh/reference/options/> alone. `devenv.nix`, `devenv.yaml`,
`devenv.lock` and devenv's `.gitignore` are all committed.

`devenv allow` is **not** run for the user: a `devenv.nix` is code that executes
on `cd`, and that consent is theirs to give. The machine's devenv service is
off, so activation is `devenv shell` by hand until somebody enables it; the
environment must work that way and the README must say so rather than assume a
hook that is not installed.

### 2. A guard at the seams that reach the human

One module-level switch, off by default, that the test base class turns on. While
it is on, the calls that change the world outside the process raise instead of
acting:

- `a11y.set_bus_property` — writes `org.a11y.Status`;
- `control.Helper.start` / `.cmd` — the virtual keyboard and pointer;
- `host.ctl` with `dispatch` — moves the human's windows.

Reads are left alone. `hyprctl -j clients` and an AT-SPI walk observe; they do
not disturb. Guarding those too would cost more in mocking than it buys, and
`index.nav()`'s deliberate `enable=False` read is exactly the shape that should
stay allowed.

The message names the seam and says what to stub, because the failure's whole
value is telling the next person what #12 took a review to notice.

### 3. A `nixosTest` for what needs a compositor

A guest running Hyprland headless with software rendering, this flake's
`ai-mirror` installed, and the suite's desktop-dependent cases run against it.
Exposed as a flake check so `nix flake check` covers it, and separately runnable.

It is **additive**. The existing sandboxed unit run stays exactly as it is and
stays the gate. If the desktop test cannot be made to work, everything above it
still lands.

### 4. `.#vm` headless, documented rather than wrapped

`QEMU_OPTS="-display none -serial mon:stdio" nix run .#vm`, ssh on 2222. A
paragraph in the docs, not a script in this repo: nixarchy owns those VMs,
olafkfreund/nixarchy#817 owns the question of which is which, and a wrapper here
would be a second place for that answer to drift.

## Alternatives rejected

- **Split local from VM by speed, and keep stubbing by hand.** The obvious
  design, and it leaves the third near-miss to whoever reviews it. Rejected on
  the evidence of the first two.
- **Guard every seam, reads included.** Safer on paper. It would force a mock in
  front of every `hyprctl` query in the suite, for calls that cannot damage
  anything, and the cost would land on every future test.
- **Drive `.#vm` over ssh from a script here.** What the intent'll have been
  imagined as. It means owning boot, readiness, port collision, teardown and a
  copy of the tree — all of which `nixosTest` already solves, in the sandbox,
  without a port.
- **Use `.#vm-big`.** Warm and quick, and shared with other work and other
  agents. A test that depends on a machine somebody else is also using is not a
  test. It is also #817's subject and moving underneath us.
- **A `shell.nix` or `devShells` output instead of devenv.** Fewer moving parts
  and no second nixpkgs. Rejected because the user asked for devenv specifically
  and the machine already carries it; noted because it remains the fallback if
  devenv's own nixpkgs proves a nuisance.
- **Enable the devenv service as part of this.** A rebuild, on a host carrying
  four CI runners, for a convenience. Out of scope by the intent's constraints.

## Risks

- **Hyprland headless in a `nixosTest` is unproven here.** Aquamarine ships a
  headless backend (`CHeadlessOutput`, outputs named `HEADLESS-n`), and nixpkgs
  tests Sway this way, but neither is proof for Hyprland 0.56 under software
  rendering in a sandbox. Design 3 is the part most likely to fail, which is why
  nothing else depends on it.
- **A guard can fail wrongly.** Someone legitimately exercising a real seam
  locally now has to turn it off, and if the switch is awkward they will disable
  it globally and we are back where we started. It has to be one obvious line in
  a test, not a ritual.
- **devenv draws a second nixpkgs** (`devenv-nixpkgs/rolling`), so a package can
  differ by a patch version from the flake's. That is devenv's design, not drift
  to fix — but it means the environment must never become what builds the
  shipped artefact. `nix build` stays the source of truth.
- **The environment can rot silently.** Nothing in CI enters it, so it can stop
  working without any check going red. Worth a cheap check that it still
  evaluates.
- **p620 carries all four nixarchy CI runners.** Nothing in this spec rebuilds
  the machine, and nothing should start doing so without the `dry-activate`
  pre-check and a note on the bus.

## Verification

**The environment.** `devenv info` evaluates and lists the expected packages.
Inside `devenv shell`, `python3 -m unittest discover -s tests` runs the suite
green **without** the hand-assembled wrapper shim from #15 — that shim not being
needed is the whole point, so it is the check.

**The guard, proven by deliberate sabotage.** Remove the `busctl` stub from the
test base class and run the suite: it must **fail**, naming the seam, and the
session bus must read the same before and after. That is #12's near-miss
reproduced on purpose, and a guard that cannot demonstrate it is not doing
anything. A `git checkout` puts the stub back.

**The desktop test.** `nix flake check` green with it included; inside the guest,
Hyprland reports a headless output and `ai-mirror windows` answers.

**Nothing regressed.** `nix flake check` green, and the sandboxed unit run still
passes with no compositor and no session bus.

**Not verified here.** That the environment behaves on any other machine or for
any other user. `devenv allow` is per user and per machine by design, and every
number and path in #15 is from this host.
